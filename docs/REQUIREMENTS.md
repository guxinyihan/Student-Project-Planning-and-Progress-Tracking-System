## 业务与计算规则

| 编号 | 规则 | 来源 |
| --- | --- | --- |
| BR-01 | 任务 assigneeId 为同项目 memberId 或 null。成员离开时协调移除活动访问并清空其分配，保留任务、状态、备注、工期和依赖，不自动重分配；保留历史备注作者引用。 | URS FR-02/NFR-04；继任细节待确认 |
| BR-02 | F4 分析输入要求 durationDays 为有限正数自然日；字段必填、保存校验及小数精度仍待 URS OQ-05 确认。无效/缺失分析输入使日程 UNAVAILABLE，不把可选分析校验擅自变成全部任务保存的批准规则。 | URS FR-03/10；DR-02 |
| BR-03 | 候选 finish-to-start 计算令预计开始跟随所有前置预计完成；独立任务并行，同一负责人不自动串行。它不锁定实际早开工或授权状态更新。 | URS DR-01/03/04；计算解释待确认 |
| BR-04 | 依赖连接同一项目的不同现存任务；不得自引用、重复或形成直接/间接环。拒绝修改时解释原因；环需说明受影响序列，并保留此前有效计划。 | §9.2、§11 |
| BR-05 | 将项目开始定义为相对 Day 0。任务 ES 为全部前置任务 EF 的最大值，无前置时为 0；EF = ES + 工期。计划工期为全部任务 EF 的最大值。反向计算 LS/LF，零总时差任务为关键活动，可能存在多条关键路径。 | §9.2–9.4 |
| BR-06 | 每次成功原子源变更递增同一 revision；所有既有项目修改带 expectedRevision。图/任务集合/工期/plannedStartDate 使相关旧日程失效或更新；状态刷新 F5 进度/阻塞；taskDeadline/asOfDate 刷新基本逾期与可选警告；projectDeadline 刷新项目比较。派生视图带当前 sourceRevision，不能把旧结果冒充当前。 | 统一架构协议；URS FR-04/12/13/15 |
| BR-07 | TaskStatus 仅 NOT_STARTED、IN_PROGRESS、COMPLETED。未完成任务存在未完成直接前置时，由 F5 另加 Blocked 警告，保留基础状态并列出该未完成直接子集；授权更新仍可进行。完成任务不派生为未完成阻塞任务。 | URS FR-04/09、DR-04 |
| BR-08 | 基础状态计数每项任务一次；Blocked 叠加计数不扣减基础计数、不增加完成率分母。非空 percentage=completedTasks/totalTasks×100；空项目 totalTasks=0、percentage=null、ProgressResult 为 NO_TASKS。具体界面文案仍待确认。 | URS FR-14/OQ-08；拟议空状态协议 |
| BR-09 | F6 保留时 FR-15 仅支持未完成逾期、被阻塞关键任务、项目预计完成超过 projectDeadline。MON-M5 基本逾期事实供 FR-13 使用，不因 F6 可选而失效；关键/项目比较须有有效当前 F4 结果。缺数据是未评估，不是无风险。 | URS FR-13/15；统一可用性协议 |
| BR-10 | 候选逾期为 status!=COMPLETED 且 taskDeadline 存在且 asOfDate>taskDeadline；项目冲突为有效当前 estimatedProjectFinish>projectDeadline。日期时区、包含截止当天及 Day0 映射待确认；截止日期不压缩 CPM。 | URS FR-15/DR-02/OQ-08；候选日期约定 |
| BR-11 | 源快照和派生视图须一致；保存失败/拒绝/冲突不递增 revision 或发布成功变更。任务删除先咨询 F3/备注引用；政策未决时以 REFERENCE_POLICY_UNRESOLVED 拒绝被引用删除，不直接改 F3 链接。取消不是新状态或已批准操作。 | URS FR-03/NFR-05；生命周期决定待确认 |

ES/EF 为最早开始/结束，LS/LF 为不延长项目结束的最晚开始/结束，总时差 = LS − ES。这里描述相对工期；相对天数如何映射为日历日期、截止日是否包含当日等尚需约定。空计划 0 天及“No tasks yet”仅保留为旧 proposal 夹具和界面候选，不能据此认定当前产品验收基线；空项目的计划可用性与具体显示仍按 URS 待决事项确认，完成比例不得除零。

### proposal 的基准例子

来源：第 5 页 §9.4；自动重算验收补充见第 6 页 §11。

| 任务 | 工期（自然日） | 前置任务 | ES | EF | 总时差 |
| --- | --- | --- | --- | --- | --- |
| A Requirements analysis | 2 | 无 | 0 | 2 | 0 |
| B Frontend development | 3 | A | 2 | 5 | 1 |
| C Backend development | 4 | A | 2 | 6 | 0 |
| D Testing | 2 | B、C | 6 | 8 | 0 |

- 原始计划为 8 天，关键活动为 A、C、D。
- C 从 4 改为 6 天后，计划为 10 天；9 天项目窗口应提示 1 天缺口。
- 从原始 4 天 C 的计划移除 C → D，保留 C 在项目内，计划为 7 天。
- 标记前置完成会解除相应阻塞；不会因此把上述完整计划的工期变为剩余工期。
