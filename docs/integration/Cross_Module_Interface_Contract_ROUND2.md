# Cross Module Interface Contract ROUND2

Status: DRAFT PENDING TEAM REVIEW. ROUND2 integration dated 25 October 2026; targeted consistency repair dated 26 October 2026. This is the proposed coordination contract for all four ROUND2 reports; the dated change/evidence index preserves the earlier snapshot and its limitations. It does not change formal URS priorities, prove customer approval, prescribe a technology, or represent implemented software.

## Ownership and module identifiers

- F1/F2 own project, membership/role, task, assignee, duration, task/project dates, saved status and progress-note records. IDs MG-M0 Management Facade; MG-M1 Project Management; MG-M2 Membership and Permission Policy; MG-M3 Task Management; MG-M4 Progress Notes. Child IDs inherit the MG prefix.
- F3 alone validates, saves/removes and supplies dependency links, including cycle rejection. It does not derive Blocked, update task status or own progress views. IDs DS-F3.1 Validation, DS-F3.2 Cycle Detection, DS-F3.3 Maintenance.
- F4 alone calculates the valid graph schedule, all critical activities and recalculation. IDs DS-F4.1 Ordering, DS-F4.2 Schedule Calculation, DS-F4.3 Critical Activities, DS-F4.4 Recalculation.
- F5 alone derives Blocked and named incomplete DIRECT prerequisites from F2 statuses plus valid F3 links; it calculates progress, raw-status counts, assigned-task views and basic overdue facts. It never writes F3 links or performs CPM.
- F6 composes the three retained FR-15 warnings from facts: unfinished overdue work, blocked critical work, project estimated finish after projectDeadline. It does not compute CPM or invent a finish date.
- Monitoring IDs MON-M0 Dashboard Builder; MON-M1 Raw Status Summary; MON-M2 Completion; MON-M3 Blocked Derivation; MON-M4 Assigned Tasks; MON-M5 Overdue Facts; MON-M6 Blocked Critical Warning; MON-M7 Project Deadline Warning. Seven functional modules plus one coordinating facade, not seven modules including M0. MON-M5 supplies basic overdue facts to F5 and, only if F6 retained, the optional FR-15 warning composer.
- SH-COORD is a shared coordination responsibility, realized through the facades; it is not a new service. It applies one MG-M2 permission policy, obtains coherent source reads, controls atomic saves/revision checks, post-save refresh and public error mapping. MG-M0 and MON-M0 do not maintain rival authorization policies. No broker, microservice or distributed transaction is introduced.

## One revision and atomic writes

SH-COORD obtains one authorized, coherent project snapshot from F1/F2 records and the F3 relationship read port. The proposed project-local revision is initialized to1 at project creation and increases once per successfully committed atomic source change, including notes, labels, assignments, roles, statuses and dates. Clients never invent the committed revision. Every existing-project mutation supplies expectedRevision. Project creation has no prior revision.

After authorization, validate against the current snapshot, verify expectedRevision at commit and atomically save all related source records plus the next revision. A lock or compare-and-save mechanism is provisional. Dependency cycle validation and version comparison belong to that same protected commit decision. If two clients add reverse links from one revision, one must conflict or revalidate after the other's commit; both cannot commit a cycle. Invalid/rejected/conflicting/save-failed requests publish no success fact, do not advance revision and preserve prior valid source/plan. User input is retained by the caller. These are design invariants, not implemented transactions.

Successful mutations return MutationResult<T> with ok, projectId, revision, value and SavedChange {projectId, revision, changeKind, affectedTaskIds, changedFields}. The conceptual post-save notification can be an ordinary coordinator call; no event broker/durable queue is required. Failures return PublicError and no private saved-record payload.

SH-COORD establishes an authorized projectId and one committed revision context while reading tasks, memberships and complete dependency edges. DependencyResultView.sourceRevision must equal the ProjectSnapshot.revision it supports. After an unrelated note or member-role change, a prior edge set need not be discarded merely because revision advanced: SH-COORD must reauthorize and prove the complete validated edge set and current task universe still agree with the coherent snapshot, or re-read them coherently, before publishing the dependency view at the current sourceRevision. Task creation/deletion, dependency edits and any change relevant to graph validity require fresh validation; a former view cannot be relabeled current without proof. If coherence cannot be proved, DependencyResultView is UNAVAILABLE with STALE_RESULT and edges=null; missing/unreadable complete input is UNAVAILABLE with DEPENDENCY_INPUT_UNAVAILABLE. F4 maps either untrusted dependency condition to its own UNAVAILABLE/DEPENDENCY_INPUT_UNAVAILABLE for nonempty tasks. No independent dependencyRevision or scheduleRevision counter is introduced. Version comparison, cycle validation and atomic save remain one protected commit decision; locks/transactions are design constraints, not implemented mechanisms.

All derived results carry sourceRevision and availability. A read reauthorizes membership even if a prior result is reused. F5/F6 accept a schedule only when its published sourceRevision matches the snapshot revision. Source graph/task creation/deletion/duration/plannedStartDate changes invalidate old applicable schedule data. Status changes refresh progress/blockers; deadline changes refresh comparisons; membership/assignee changes refresh access and assignment views.

Reuse is allowed only after the coordinator verifies the relevant schedule inputs against the new coherent snapshot. It may retain relative timing values only if task IDs, graph and durations are unchanged, remap absolute finish if plannedStartDate changed, refresh labels/date comparisons as needed and publish a fresh result with the current sourceRevision. If that proof/refresh cannot be made, return UNAVAILABLE with STALE_RESULT, not old values as current. No second schedule-input counter is introduced. asOfDate changes are reads and do not increment source revision.

## Numeric precision policy proposed under D-03 and D-07

This language-independent recommendation supports positive finite durationDays values, including decimals; it does not impose an approved integer-only or fixed-scale business rule. Preserve the canonical base10 input digits. Keep computation precision separate from presentation, and never round intermediate forward/backward values. The existing CPM formulas remain ES=max predecessor EF, EF=ES+duration, T=max terminal EF, LF=min successor LS (T for terminals), LS=LF-duration and totalFloat=LS-ES.

Preferred NumericPolicy uses exact base10 decimal or equivalent rational arithmetic for the canonical finite-decimal inputs. In this exact representation a certified mathematical totalFloat=0 identifies critical activities; any genuine positive float is noncritical. This is not an unexplained binary-float equality test. A displayed rounded zero is never used for classification, and F5/F6 consume only the F4-certified criticalTaskIds, without local epsilon rules.

If detailed design instead retains a binary floating backend, one central policy must establish certified error intervals from input conversion, validated input scale/range, operation rounding and graph propagation for the chosen language/library. Use outward-rounded bounds for addition/subtraction, max/min on predecessor/successor interval endpoints and the same CPM recurrence to enclose totalFloat. A positive interval excluding zero certifies noncriticality. An interval containing zero, or an apparent negative/invariant conflict, requires recomputation from canonical inputs with exact arithmetic or a higher-precision proof; it is not automatic permission to label a task critical. This is the shared tolerance decision rule, not an arbitrary fixed epsilon. If reliable timing/criticality cannot be established, return whole ScheduleResultView UNAVAILABLE/CALCULATION_FAILED with null schedule facts and an authorized explanatory notice, never a partial current critical set. Concrete backend, supported input limits, derived bounds and display format require D-03/D-07 review and validation; no particular epsilon is frozen here.

Recommended candidate absolute-date mapping uses the canonical unrounded, NumericPolicy-resolved T. Do not apply ceil to a display-rounded value or to an unresolved binary artifact just above an integer. If a binary interval straddles an integer boundary, resolve the canonical value before date mapping. IT26's exact tie and genuine tiny-positive-slack cases are conditional oracles for this proposed policy, not executed application tests.

## Invalid duration diagnostics and core-save separation

F4 checks the complete authorized current task set after the feature/empty/dependency gates. Every duration used for analysis must be present, numeric, finite and strictly positive. Invalid values make the whole nonempty schedule UNAVAILABLE/INVALID_INPUT; durationDays, timings, criticalTaskIds and estimatedProjectFinish remain null. No partial path or zero-duration substitute is published. This analysis failure alone neither rejects an otherwise policy-valid F2 save nor rolls back a successful source commit. Whether F2 permits a task with omitted planning metadata, and how it validates supplied estimates, remain D-03 decisions; there is no fourth draft/cancelled TaskStatus.

An optional ScheduleResultView.diagnostics field carries DurationInputDiagnostic[] only for an authorized INVALID_INPUT result. DurationInputDiagnostic = {taskId:TaskId, field:"durationDays", issue:MISSING|NON_NUMERIC|NON_FINITE|NON_POSITIVE, message:string}. It identifies every detectable invalid task/field within that already authorized coherent project context. The diagnostic is validation information, not a partial valid schedule payload or a new top-level reasonCode. Other result states use diagnostics=null. Do not leak diagnostics, task IDs/names, existence, memberships or private values through denied/unknown references: apply the existing generic PublicError before analysis. The sourceRevision binds authorized diagnostics to the current attempted snapshot, without advancing the source revision or publishing SavedChange.

Safe F5 progress, raw states, assignments and independent overdue facts continue. With valid current F3 links and statuses, MON-M3 still derives current Blocked facts/direct incomplete reasons. Enabled F6 may evaluate independent overdue warnings; blocked-critical/project-finish types require the unavailable current F4 facts and stay unevaluated. IT27 tests this boundary, including safe generic access errors; synthetic invalid analysis fixtures do not assert that F2 accepts malformed records.

## Availability and nullable schedule facts

ScheduleAvailability = VALID | NO_TASKS | NOT_ENABLED | UNAVAILABLE.

- VALID: a nonempty valid plan has coherent timings, durationDays and the full criticalTaskIds set. estimatedProjectFinish is present only when a valid plannedStartDate/date mapping is available; otherwise it is null with finishReasonCode=MISSING_PLANNED_START or DATE_MAPPING_UNRESOLVED, while relative duration remains valid.
- NO_TASKS: enabled analysis of an empty task list; durationDays=null, criticalTaskIds=null and estimatedProjectFinish=null. Do not fabricate0-day delivery or0% completion. A design-specific display such as No tasks yet remains proposed, not approved wording.
- NOT_ENABLED: F4 not retained/enabled; schedule payload fields null; reasonCode=FEATURE_NOT_ENABLED.
- UNAVAILABLE: reasonCode is INVALID_INPUT, CALCULATION_FAILED, STALE_RESULT or DEPENDENCY_INPUT_UNAVAILABLE; payload fields null and unsupported current warnings hidden. A missing critical set is unknown, not an empty known set. isCritical is null when not evaluable, never false as a stand-in for unavailable.

Evaluate F4 gates in order: F4 off -> NOT_ENABLED/FEATURE_NOT_ENABLED; F4 enabled with no tasks -> NO_TASKS; F4 enabled with nonempty tasks but no complete, valid, same-revision dependency view -> UNAVAILABLE/DEPENDENCY_INPUT_UNAVAILABLE. Only then calculate a current schedule from valid inputs. A VALID dependency view may contain edges=[]; edges=null never satisfies this gate. No valid dependency-free override is approved.

| Result | Permitted reasonCode and conditions |
| --- | --- |
| ScheduleResultView | NOT_ENABLED -> FEATURE_NOT_ENABLED. UNAVAILABLE -> INVALID_INPUT (invalid schedule inputs), CALCULATION_FAILED (analysis failed), STALE_RESULT (previous schedule cannot be proved current), or DEPENDENCY_INPUT_UNAVAILABLE (required complete current F3 input absent/untrusted). VALID and NO_TASKS have no failure reasonCode. |
| DependencyResultView | NOT_ENABLED -> FEATURE_NOT_ENABLED. UNAVAILABLE -> DEPENDENCY_INPUT_UNAVAILABLE (missing/unreadable complete dependency input), INVALID_INPUT (invalid dependency records/graph), or STALE_RESULT (coherence with current snapshot cannot be proved). CALCULATION_FAILED is not a dependency-read reason. VALID and NO_TASKS have no failure reasonCode. |
| BlockedResult | NOT_ENABLED -> FEATURE_NOT_ENABLED. UNAVAILABLE carries the applicable dependency-input/invalid-input/stale reason from its required dependency facts; it has no F4 CALCULATION_FAILED reason. Unknown isBlocked flags, blockedTaskIds and byTaskId payloads remain null rather than false/empty; reasonCode still explains the unavailable capability. |
| ProgressResult and OverdueResult | Safely readable coherent source facts use VALID or NO_TASKS. They do not inherit F4 reasons. Missing taskDeadline is recorded per task in notEvaluatedTaskIds/reasons, not converted to a schedule failure. |
| ScheduleWarningResult | F6 off -> NOT_ENABLED/FEATURE_NOT_ENABLED with null warning payload. When enabled, evaluationByType carries only the reason applicable to that type's unavailable inputs; schedule-dependent types may propagate the corresponding F4 reason. Independent overdue evaluation uses current MON-M5 facts and does not inherit an F4 failure. Date-specific finishReasonCode or missing-date explanations remain separate. |

ScheduleResultView = {availability, sourceRevision, reasonCode?, durationDays:number|null, timings:TaskTiming[]|null, criticalTaskIds:TaskId[]|null, estimatedProjectFinish:LocalDate|null, finishReasonCode?, diagnostics:DurationInputDiagnostic[]|null}. TaskTiming has taskId, ES, EF, LS, LF, totalFloat. Absolute finish is supplied by F4, not derived anew in F5/F6.

DependencyResultView reuses the availability values for its own F3 capability: F3 off -> NOT_ENABLED with FEATURE_NOT_ENABLED and edges=null; F3 enabled with an empty task universe -> NO_TASKS with edges=[]; F3 enabled with nonempty tasks and a complete valid edge set -> VALID, including edges=[] when no dependency edges exist. Missing/inaccessible/invalid dependency input uses edges=null. A missing F3 feature must not turn missing links into an empty valid graph. F4 needs a trustworthy complete graph: if F3 is off or unavailable it cannot silently assume all tasks independent; for enabled F4 with nonempty tasks return UNAVAILABLE with reasonCode=DEPENDENCY_INPUT_UNAVAILABLE. F4 off and enabled empty tasks are handled by the preceding gates, not by this reason. No extra dependency-free mode is approved here.

ProgressResult = {availability:VALID|NO_TASKS, sourceRevision, totalTasks, completedTasks, percentage:number|null}. total=0 => NO_TASKS and percentage=null; otherwise completed/total*100. RawStatusCounts count all tasks once by stored TaskStatus; blockedCount/blockedTaskIds are a separate overlay and never subtract from NOT_STARTED/IN_PROGRESS or increase the denominator. Completed tasks are absent from blocked work. An unfinished task is blocked iff at least one direct prerequisite is not COMPLETED. Name only that incomplete direct subset. Authorized status updates remain available; completion-before-prerequisites and final transition policy are still open.

BlockedResult = {availability, sourceRevision, blockedTaskIds:TaskId[]|null, byTaskId:...|null, reasonCode?}. For a safely known empty task universe, NO_TASKS has blockedTaskIds=[] and byTaskId={}; enabled empty dependency data likewise has edges=[]. NOT_ENABLED/UNAVAILABLE blocker or dependency payloads are null. Schedule NO_TASKS still has null duration/critical/finish because those facts are not meaningful. Empty payload meanings are type-specific and never convert unknown data into a known empty result. Unknown dependency data yields unknown flags, not false. getAssignedTasks returns {availability, sourceRevision, items}; item rawStatus is independent from nullable isBlocked/isCritical. Requested sorting is a proposed UI choice, not a new priority field.

## Dashboard and warning degradation

buildDashboardSummary(projectId, actorId, asOfDate): DashboardResult.
DashboardResult = {ok:true, summary:DashboardSummary} OR {ok:false,error:PublicError}.
DashboardSummary carries projectId, name, revision, asOfDate, progress, rawStatusCounts, blockedResult, assignedTasks, overdueResult, schedule (ScheduleResultView), warnings (ScheduleWarningResult), and availability notices.

Reject a full dashboard only when access/project resolution fails or F1/F2 source data cannot be safely read coherently. A schedule-only failure, stale result, disabled F4 or unavailable F3 view does not fail the whole dashboard. Return reliable raw statuses, completion, assignment and basic overdue facts. Return blocker details only when valid dependency data exists. Mark unavailable capabilities and suppress unsupported current critical/finish warnings. Do not map schedule-only STALE_RESULT to a top-level fatal dashboard error.

OverdueResult carries availability (VALID or NO_TASKS), sourceRevision, asOfDate, overdueTaskIds and notEvaluatedTaskIds/reasons for missing taskDeadline; missing dates are not explicit on-time assertions. With coherent source data, basic overdue facts remain available regardless of F4/F6. If F6 is not retained, the FR-13 overdue list still works but FR-15 warning composition is NOT_ENABLED.

When F6 is retained, ScheduleWarningResult carries availability, sourceRevision, items and evaluationByType for overdue, blockedCritical and projectDeadline. With safe current tasks, valid taskDeadline/asOfDate and MON-M5 available, the basic FR-13 overdue list remains available during F4 failure. If F6 is enabled, OVERDUE_TASK can still be independently evaluated from those facts; BLOCKED_CRITICAL_TASK and PROJECT_DEADLINE_CONFLICT remain unevaluated when their required current criticalTaskIds or estimatedProjectFinish is unavailable. Unevaluated means unknown, not no risk. F6 off never makes FR-15 available, and FR-15 remains Could Have. A safely assembled partial result may have availability=VALID while individual evaluationByType entries are UNAVAILABLE; empty items does not prove no risk when a type is unevaluated. When F6 is off use NOT_ENABLED and null warning payload. Never upgrade FR-15's formal Could priority. Blocked-critical needs known F5 blockers plus current valid F4 criticalTaskIds; project conflict needs current valid estimatedProjectFinish and known projectDeadline. NO_TASKS is a neutral no-work state, not no-risk proof about a missing schedule.

## Public errors and privacy

Internal PROJECT_NOT_FOUND, TASK_NOT_FOUND, CROSS_PROJECT_REFERENCE, NOT_MEMBER etc. may support diagnostics without private payloads. At the user boundary, unknown/nonmember/inaccessible project references use INVALID_OR_INACCESSIBLE_PROJECT with 'Invalid or inaccessible project.' Task references use INVALID_OR_INACCESSIBLE_TASK with 'Invalid or inaccessible task.' Do not reveal existence, private names/titles, memberships or saved values. Authorized project contexts may receive detailed self-link/duplicate/cycle/input errors. PERMISSION_DENIED and LEADER_AGREEMENT_REQUIRED apply only after accessible membership context is established. Other proposed outcomes: INVALID_INPUT, INVALID_STATUS, INVALID_DEPENDENCY, CIRCULAR_DEPENDENCY, REVISION_CONFLICT, REFERENCE_POLICY_UNRESOLVED, SAVE_FAILED and SOURCE_UNAVAILABLE. Analysis unavailable is a view state/reason, not normally a fatal dashboard error. Failures carry no successful change record or fabricated current data. No approval workflow is added.

## Lifecycle and dates still requiring decisions

Member departure is a coordinated F1/F2 transaction removing active membership/access and setting affected assigneeId=null while retaining tasks, dependencies, notes, statuses and durations. Preserve stable historical author references for retained notes; the storage/history representation is deferred to detailed design, and departure must not create broken note-author references. Do not cancel, delete, auto-reassign or serialize parallel work. Sole-leader departure/role succession remains unresolved and must not silently orphan permissions. Task deletion consults F3 dependency and note-reference ports. With unresolved reference policy, reject a referenced deletion as REFERENCE_POLICY_UNRESOLVED. A later agreed cleanup must be coordinated with F3 and notes atomically; F1/F2 never directly edits F3 links. Task cancellation is not a fourth status or a supported new operation; it needs scope confirmation. Initial NOT_STARTED is a design proposal, not an independently approved status-transition requirement.

Recommended candidate date policy under PENDING D-04: calendar days, including weekends/holidays; Day0 is plannedStartDate. If the policy is explicitly selected for a conditional paper test or later approved, estimatedProjectFinish = plannedStartDate + ceil(T) calendar days, using the full canonical unrounded NumericPolicy-resolved project duration T. For integer T this is start+T; for decimal T do not use display rounding or an unresolved binary excess. Task overdue iff status!=COMPLETED, taskDeadline is known and asOfDate>taskDeadline. Project conflict iff current valid estimatedProjectFinish and projectDeadline are known and estimatedProjectFinish>projectDeadline. Equality triggers neither comparison. LocalDate values follow the to-be-agreed project calendar/timezone; chat/report timezone grants no approval. Missing plannedStartDate yields MISSING_PLANNED_START; absent/unconfirmed date mapping yields DATE_MAPPING_UNRESOLVED, with finish=null and corresponding comparisons unevaluated while reliable relative analysis may remain VALID. Missing task/project dates similarly yield unevaluated comparisons, not safety. Deadlines never constrain CPM. IT12/16/21/22 are conditional on explicit adoption of this candidate for the scenario, not evidence of customer approval.
